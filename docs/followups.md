## DAFTARI-102 — short-lived WebSocket tickets (assessment)

- Exposure today: the dashboard's 12h session JWT is appended as `?token=` on the `/ws` upgrade. It is visible to anything that records the request URL — Cloudflare/origin access logs, any proxy or CDN in front of the worker, and browser history. The transport is `wss://`, so the token is not exposed in transit to a passive observer; the risk is log/side-channel capture of a long-lived credential.
- Ticket alternative: the client calls an authenticated HTTP endpoint (e.g. `POST /realtime/ticket`) with its normal Bearer JWT; the api worker mints a single-use, ~30s ticket bound to the tenant, and the client opens `/ws?ticket=`. The `/ws` handler consumes the ticket once and rejects replays and expired tickets.
- Costs: one extra authenticated round trip per (re)connect — noticeable on flaky networks and on the dashboard's auto-reconnect path; single-use semantics need server state (KV/DO with TTL + consume); and new failure modes appear (ticket expiry mid-reconnect, clock skew, cleanup of unspent tickets) plus another endpoint to secure.
- Benefit: a captured URL yields only a ~30s, single-use, tenant-scoped ticket instead of a 12h bearer token — it removes the log-leak replay window.
- Recommendation: do NOT implement for Phase 1. The `?token=` contract is acceptable as shipped: first-party worker, `wss://`, 12h TTL, and logs we control. Ticket state plus a round trip is cost without a demonstrated threat.
- Revisit trigger (any one): (1) access logs leave our control or are exported (Logpush, third-party CDN, or retention longer than the token TTL); (2) a security review or pen-test flags URL credentials; (3) session-JWT TTL is shortened or per-connection re-auth is required. When triggered, implement the mint/consume ticket flow above.
